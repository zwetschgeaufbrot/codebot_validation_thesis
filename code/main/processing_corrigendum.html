Check for Human Error in Manually Coded Entries

After visually inspecting the data, it is evident that there are multiple sources of minor, fixable errors introduced by a) manual coding, b) working with the .csv files across different operating systems c) the adjudication programming. The following reflects my attempt to clean up the data as best as I can with the limitation that there is no second set of eyes to validate my approach. Rows containing (minorly) modified observations will get flagged in a separate boolean variable corrected. Another boolean variable (exclude) will flag observations with major issues that warrant exclusion from the inferential analyses. See below a list of spotted data quality issues after visually inspecting the data and comparing it to the sample_coding_human.xlsx file.

Caution

While the first source of error was anticipated in the pre-registration, this was not the case for the latter two. However, I consider the assessment of the latter error sources to be crucial for the validity of the results which is why I will flag them during processing.

List of observed errors:

  • In the data from Hsieh et al., the columns manuscript_content through results for the inference criteria were coded as NA\r\n. Since the \r\n part are Window’s “invisible” characters signaling Carriage Return \r and Line Feed \n, they create the weird situation where those cells are neither recognized by is.na() nor by directly filtering for “NA”. Apparently, read_csv() also did not recognize them as NA_characters and neither did the adjudicator which was supposed to replace rows which only had NAs with empty strings throughout. NA:NA in human_code_location resulted from the adjudicator aggregating across the given file and code line quote. This should also be empty instead of NA. -> Change these cells to “” (because the NA coding needs to be fixed later).

  • Inconsistent use of delimiters when it comes to manuscript location quotes - Missing manuscript content in cases where manuscript location and a judgement are given and a comparison to the original excel sheet makes it evident that there must have been a copy & paste error involved -> Flag but do not correct because this would alter the adjudicator’s judgement.

  • Dimensions were numbered for clarity during manual coding, not all numbers were removed.

Sanity Check NAs

Currently, there is an issue with the meaning of NAs across the 3 judgement variables.

Human_match_judgement takes on this value both when manuscript information is present and when it is not. This should not be the case as an NA in the sense of “indecisiveness” is different from NA in the sense of missingness. I will change meaningful NAs to 99 and cases where there is no manuscript content coded to NA. Once the match variable has been transformed, I will replace human_match_judgement with NA whenever no quote was provided so that NA truly reflects absence and 99 uncertainty.

Codebot_match_judgement takes on the values 1/0/NA and there are no empty string entries by CodeBot. Thus the match judgement will become 99 in cases where it was previously NA.

Codebot_human_agreement is currently NA in cases where both raters rated “meaningful” NA but also NA when one rater’s info is missing. Cases where one rater’s rating is missing should stay NA because it indicates the absence of assessable agreement, but cases where both raters coded info and judged “meaningful” NA, the adjudicator’s rating should be 99.
